# diary-entries Specification

## Purpose

사용자가 하루에 한 줄씩 짧은 기록을 남기고, 지금까지 남긴 기록을 최신순으로 다시 볼 수 있게 하는 다이어리의 핵심 기능이다.

## Requirements

### Requirement: 오늘 날짜 표시
시스템은 화면에 오늘 날짜를 `YYYY-MM-DD` 형식으로 SHALL 표시한다. 날짜는 사용자 기기의 로컬 시간대를 기준으로 계산해야 하며 UTC 기준이어서는 MUST NOT 한다.

#### Scenario: 화면을 열면 오늘 날짜가 보인다
- **WHEN** 사용자가 로컬 시간 2026년 12월 31일에 다이어리를 연다
- **THEN** 화면에 `2026-12-31`이 표시된다

#### Scenario: UTC 날짜와 로컬 날짜가 다른 시각
- **GIVEN** 사용자 기기의 시간대가 UTC+9이다
- **WHEN** 사용자가 로컬 시간 2026-12-31 08:30에 다이어리를 연다 (UTC로는 2026-12-30)
- **THEN** 화면에 `2026-12-31`이 표시된다

### Requirement: 한 줄 기록 저장
시스템은 사용자가 입력창에 쓴 한 줄을 저장 버튼 또는 Enter 키로 SHALL 저장한다. 각 기록에는 내용, 로컬 기준 작성 날짜(`YYYY-MM-DD`), 작성 시간(`HH:mm`)이 MUST 함께 저장된다. 저장에 성공하면 입력창은 비워진다.

#### Scenario: 저장 버튼으로 저장
- **WHEN** 사용자가 "오늘 산책했다"를 입력하고 저장 버튼을 누른다
- **THEN** 해당 내용이 현재 날짜·시간과 함께 기록으로 저장된다
- **AND** 입력창이 비워진다

#### Scenario: Enter 키로 저장
- **WHEN** 사용자가 내용을 입력하고 Enter 키를 누른다
- **THEN** 저장 버튼을 누른 것과 같이 기록이 저장된다

### Requirement: 같은 날 여러 번 작성
시스템은 같은 날짜에 여러 개의 기록을 SHALL 허용한다. 새 기록은 같은 날짜의 기존 기록을 덮어쓰지 MUST NOT 한다.

#### Scenario: 같은 날 두 번 저장
- **GIVEN** 2026-12-31 09:00에 저장한 기록이 하나 있다
- **WHEN** 사용자가 같은 날 14:05에 새 기록을 저장한다
- **THEN** 2026-12-31 날짜의 기록이 두 개가 되고, 각각 `09:00`과 `14:05` 시간을 가진다

### Requirement: 잘못된 입력 거부
시스템은 비어 있거나 공백 문자만 있는 입력을 SHALL NOT 저장하며, 이때 내용을 입력하라는 경고 메시지를 MUST 표시한다. 입력은 앞뒤 공백을 제거한 뒤 최대 100자까지 MUST 허용되며, 그보다 긴 내용은 입력할 수 없어야 한다.

#### Scenario: 빈 입력
- **WHEN** 사용자가 아무것도 입력하지 않거나 공백만 입력하고 저장한다
- **THEN** 기록이 저장되지 않고 목록이 바뀌지 않는다
- **AND** "내용을 입력해 주세요" 경고 메시지가 표시된다

#### Scenario: 경고 메시지 사라짐
- **GIVEN** 빈 입력 경고가 표시되어 있다
- **WHEN** 사용자가 입력창에 글자를 입력한다
- **THEN** 경고 메시지가 사라진다

#### Scenario: 앞뒤 공백 제거
- **WHEN** 사용자가 "  산책  "을 입력하고 저장한다
- **THEN** 기록 내용은 "산책"으로 저장된다

#### Scenario: 100자 제한
- **WHEN** 사용자가 100자를 넘게 입력하려고 한다
- **THEN** 입력창에는 100자까지만 들어간다

### Requirement: 기록 유지
시스템은 저장된 기록을 브라우저에 SHALL 보관하여, 페이지를 새로고침하거나 브라우저를 다시 열어도 기록이 유지되어야 한다.

#### Scenario: 새로고침 후에도 기록 유지
- **GIVEN** 사용자가 기록 3개를 저장했다
- **WHEN** 사용자가 페이지를 새로고침한다
- **THEN** 같은 기록 3개가 목록에 다시 표시된다

### Requirement: 저장 실패 처리
브라우저 저장소에 기록을 쓸 수 없을 때 시스템은 사용자에게 저장에 실패했다는 안내를 SHALL 보여 주고, 화면은 계속 동작해야 MUST 한다. 실패한 경우 입력 내용은 지워지지 않는다.

#### Scenario: 저장소 사용 불가
- **GIVEN** 브라우저 저장소에 쓰기가 실패하는 환경이다 (예: 저장 공간 부족)
- **WHEN** 사용자가 기록을 저장한다
- **THEN** 저장 실패 안내가 표시된다
- **AND** 입력창의 내용이 그대로 남아 있다

#### Scenario: 저장된 데이터가 손상됨
- **GIVEN** 브라우저 저장소의 기록 데이터를 읽을 수 없는 형식이다
- **WHEN** 사용자가 다이어리를 연다
- **THEN** 화면이 오류 없이 열리고 빈 목록으로 표시된다

### Requirement: 기록 목록 표시
시스템은 저장된 모든 기록을 작성 시각 기준 최신순으로 SHALL 보여 준다. 각 항목에는 날짜(`YYYY-MM-DD`), 시간(`HH:mm`), 내용이 MUST 표시된다. 기록이 없으면 비어 있음을 알리는 안내를 보여 준다.

#### Scenario: 최신 기록이 맨 위
- **GIVEN** 2026-12-30 22:40과 2026-12-31 09:12에 저장한 기록이 있다
- **WHEN** 사용자가 목록을 본다
- **THEN** 2026-12-31 09:12 기록이 맨 위에 표시된다

#### Scenario: 저장 직후 목록 반영
- **WHEN** 사용자가 새 기록을 저장한다
- **THEN** 새로고침 없이 목록 맨 위에 그 기록이 나타난다

#### Scenario: 기록 없음
- **WHEN** 저장된 기록이 하나도 없는 상태에서 다이어리를 연다
- **THEN** 목록 영역에 기록이 없다는 안내가 표시된다

### Requirement: 목록 스크롤
목록 영역은 약 5개 항목 높이로 SHALL 고정된다. 기록이 그보다 많으면 페이지 전체가 아니라 목록 영역 안에서 MUST 스크롤된다.

#### Scenario: 5개 이하
- **GIVEN** 기록이 5개 이하이다
- **WHEN** 사용자가 목록을 본다
- **THEN** 모든 기록이 스크롤 없이 보인다

#### Scenario: 5개 초과
- **GIVEN** 기록이 8개 있다
- **WHEN** 사용자가 목록을 본다
- **THEN** 최신 기록 약 5개가 보이고, 나머지는 목록 영역을 스크롤해서 볼 수 있다

### Requirement: 기록 수정 시작과 취소
목록의 각 기록은 수정 버튼을 SHALL 제공한다. 수정 버튼을 누르면 그 기록이 기존 내용이 채워진 입력창과 저장·취소 버튼으로 바뀌어야 MUST 한다. 취소 버튼이나 Esc 키를 누르면 저장하지 않고 수정 전 표시로 돌아가야 한다. 한 번에 한 기록만 수정 상태일 수 있다.

#### Scenario: 수정 시작
- **GIVEN** 목록에 "산책했다" 기록이 있다
- **WHEN** 사용자가 그 기록의 수정 버튼을 누른다
- **THEN** 그 줄에 "산책했다"가 채워진 입력창과 저장·취소 버튼이 나타나고 입력창에 포커스가 간다

#### Scenario: 취소로 되돌리기
- **GIVEN** 사용자가 "산책했다"를 "산책 30분"으로 고치는 중이다
- **WHEN** 취소 버튼이나 Esc 키를 누른다
- **THEN** 기록은 "산책했다"로 표시되고 저장된 내용도 바뀌지 않는다

#### Scenario: 다른 기록 수정 시작
- **GIVEN** 기록 A를 수정하는 중이다
- **WHEN** 사용자가 기록 B의 수정 버튼을 누른다
- **THEN** 기록 A의 수정은 저장되지 않고 취소되며, 기록 B가 수정 상태가 된다

### Requirement: 기록 내용 수정 저장
시스템은 저장 버튼이나 Enter 키로 수정한 내용을 SHALL 저장한다. 수정해도 기록의 작성 날짜·시간과 목록 속 위치는 MUST NOT 바뀐다. 내용이 실제로 바뀐 경우에만 수정 시각을 함께 저장한다. 저장한 수정 내용은 새로고침 후에도 유지되어야 한다.

#### Scenario: 수정 저장
- **GIVEN** 2026-12-30 22:40에 쓴 "산책했다" 기록이 있다
- **WHEN** 사용자가 내용을 "산책 30분"으로 고치고 Enter 키를 누른다
- **THEN** 그 기록은 "산책 30분"으로 표시되고, 날짜·시간은 `2026-12-30 22:40` 그대로이며 목록 속 위치도 그대로다

#### Scenario: 새로고침 후 유지
- **GIVEN** 사용자가 기록을 수정해 저장했다
- **WHEN** 페이지를 새로고침한다
- **THEN** 수정된 내용이 그대로 표시된다

#### Scenario: 바뀌지 않은 내용 저장
- **WHEN** 사용자가 수정 상태에서 내용을 바꾸지 않고(앞뒤 공백만 바꾼 경우 포함) 저장한다
- **THEN** 수정 상태가 끝나고, 그 기록은 수정된 것으로 표시되지 않는다

### Requirement: 수정 입력 검증
수정 입력은 새 기록 작성과 같은 규칙을 SHALL 따른다. 앞뒤 공백을 제거하고 최대 100자까지 허용한다. 비어 있거나 공백만 있는 내용은 MUST NOT 저장하며, 이때 "내용을 입력해 주세요." 경고를 보여 주고 수정 상태를 유지한다. 빈 내용으로 수정해도 기록은 삭제되지 않는다.

#### Scenario: 빈 내용으로 수정 저장
- **GIVEN** 사용자가 기록을 수정하는 중이다
- **WHEN** 내용을 모두 지우거나 공백만 남기고 저장한다
- **THEN** 기록은 바뀌지 않고, "내용을 입력해 주세요." 경고가 표시되며, 수정 상태가 유지된다

#### Scenario: 경고 후 다시 입력
- **GIVEN** 빈 내용 경고가 표시되어 있다
- **WHEN** 사용자가 수정 입력창에 글자를 입력한다
- **THEN** 경고가 사라진다

#### Scenario: 100자 제한
- **WHEN** 사용자가 수정 입력창에 100자를 넘게 입력하려고 한다
- **THEN** 입력창에는 100자까지만 들어간다

### Requirement: 수정 저장 실패 처리
수정 내용을 브라우저 저장소에 쓸 수 없을 때 시스템은 저장 실패 안내를 SHALL 보여 주고, 수정 상태와 입력 중인 내용을 MUST 유지한다.

#### Scenario: 저장소 쓰기 실패
- **GIVEN** 브라우저 저장소에 쓰기가 실패하는 환경이다
- **WHEN** 사용자가 수정 내용을 저장한다
- **THEN** 저장 실패 안내가 표시되고, 수정 입력창과 입력한 내용이 그대로 남아 있다

### Requirement: 수정됨 표시
내용이 수정된 기록은 목록에서 "(수정됨)" 표시를 SHALL 함께 보여 준다. 한 번도 수정되지 않은 기록에는 표시하지 MUST NOT 한다.

#### Scenario: 수정된 기록 표시
- **GIVEN** 기록 A는 수정되었고 기록 B는 수정되지 않았다
- **WHEN** 사용자가 목록을 본다
- **THEN** 기록 A에는 "(수정됨)"이 보이고 기록 B에는 보이지 않는다

### Requirement: 수정 중 새 기록 작성
한 기록을 수정하는 중에 상단 입력창으로 새 기록을 저장해도, 수정 중인 기록의 수정 상태와 입력 중인 내용은 SHALL 유지되어야 한다.

#### Scenario: 수정 중 새 기록 저장
- **GIVEN** 기록 A를 "고치는 중"으로 수정하는 중이다
- **WHEN** 사용자가 상단 입력창에 새 기록을 써서 저장한다
- **THEN** 새 기록이 목록 맨 위에 추가되고, 기록 A는 여전히 "고치는 중"이 입력된 수정 상태로 남아 있다
